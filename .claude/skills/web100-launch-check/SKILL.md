# Woohop 上線後驗收

新專案部署完不等於上線完成。這個 skill 走一輪固定的驗收，重點在**抓那些「部署成功但其實壞掉／漏掉」的狀況**——它們不會讓部署失敗，只會安靜地讓流量、追蹤或索引出問題，往往幾週後才發現。

## 開始之前：確認在測「正式網址」

這是整份流程最重要的前提。**本機測過不算數**，因為正式網域上有一層 Vercel rewrite 代理，很多問題只在那層之後才出現（WebSocket 升級、CORS、資源路徑、語言轉址）。

先確認三件事，缺一不可：

1. **正式網址**是什麼（例：`https://www.vibeweb100.com/match/`）
2. **Worker／部署來源**的網址（例：`https://web100-03-preference-match.shiki0akira.workers.dev`）
3. 專案在本機的**路徑與路徑代號**（例：`web100_03_PreferenceMatch`、`/match/`）

不確定就去 `docs/ARCHITECTURE.md` 第 9 節的進度表，或該專案的 `CONCEPT.md` / `README.md` 查。

還有一個每次都會咬人的陷阱：**部署完立刻用瀏覽器驗，很可能看到舊版**。判斷「線上到底是不是新版」一律用 `curl` 直接抓檔案內容比對，不要靠瀏覽器畫面。瀏覽器（尤其行動裝置與內嵌 WebView）即使收到 `must-revalidate` 也常常拿快取。

## 流程

以下五段照順序做。每段結束時把結果彙整成表，最後一次交給使用者，不要每查一項就回報一次。

### 1. 線上煙霧測試

先跑該專案自己的自動化測試——大多數 Woohop 專案有 `npm run test:smoke` 之類的端對端測試，而且吃環境變數指定對象：

```bash
MATCH_URL=https://www.vibeweb100.com npm run test:smoke
```

**這裡有個重要的判讀**：如果專案是 WebSocket 架構（Durable Object），對著正式網域跑煙霧測試**很可能會失敗，而且那是對的**。因為架構上「網頁走 Vercel 代理、API 與 WebSocket 由客戶端直連 Worker」——測試腳本從網址推導 WS 位址，就會試著連 `wss://www.vibeweb100.com/...`，那條路本來就不通。

遇到這種情形，改用瀏覽器在正式網域上實測真正的流程（`app.js` 的 `API_ORIGIN` 會自動切到 Worker）：開房 → 確認房號、QR code 畫出來、WebSocket 狀態是 `OPEN`、名單有人、**console 沒有錯誤**。詳細做法見 `references/checks.md` 的「WebSocket 專案怎麼驗」。

同時用 `scripts/check-live.sh` 掃基本的 HTTP 狀態（見下一段）。

### 2. SEO 中繼標籤與索引前置

跑 `scripts/check-live.sh <正式網址前綴> <語言清單>`，它會一次檢查：

- 每個語言的頁面、規則頁、sitemap 是否 200
- 不帶語言的路徑會不會依語言 302 轉址
- `canonical` 是否指向自己（不是別的語言、不是 workers.dev）
- `hreflang` 是否涵蓋所有語言且有 `x-default`
- `og:title` / `og:description` / `og:url` / **`og:image`**
- 亂打的路徑是否回 404（而不是 200 的空白頁）
- `robots.txt` 有沒有列出這支新的 sitemap

**`og:image` 特別容易漏**，而它對這個系列的傳播影響很大：主要分享管道是 LINE 群組，沒有 og:image 就沒有縮圖預覽，連結看起來像可疑訊息。截至目前整個系列都還沒有，發現缺少時要明確告訴使用者，不要當成小事帶過。

### 3. GA4 事件盤點與驗證

分兩層做，兩層都要。

**第一層：盤點有沒有漏事件。** 拿新專案跟系列裡最接近的既有專案對照，看漏斗是不是完整。用 `scripts/ga4-events.sh` 列出各專案送出的事件名稱：

```bash
bash scripts/ga4-events.sh
```

漏斗至少要能回答這四個問題，缺任何一段就等於看不到轉換率：

| 問題 | 對應事件 |
|---|---|
| 有多少人開了房間？ | `<前綴>_room_created` |
| 有多少人真的加入？ | `<前綴>_player_joined` |
| 有多少房間真的開始玩？ | `<前綴>_game_started` |
| 有多少玩到看見結果？ | `<前綴>_results_shown` 或等價的結束事件 |

**「開了房沒玩」與「真的玩完」分不出來**是最常見的缺口——這種事件在寫程式時最容易忘，因為它不影響任何功能。發現缺的就直接補上，不要只是列出來。

補事件時遵守系列既有的三條規則（違反了資料會直接失真）：

- **事件名一律加專案前綴**（`avalon_` / `buzzer_` / `match_`）。整個系列共用同一個 GA4 資源，沒有前綴就分不出是哪個遊戲的。
- **只在「做那個動作的那台裝置」上送**。狀態是廣播給全場的，照著狀態送的話，一場 10 個人的遊戲會把同一個事件記 10 次。
- **`page_view` 手動送**。多個畫面共用同一個網址，靠 `send_page_view` 自動送只會記到一筆。

**第二層：確認資料真的有進來。** 程式碼裡有事件不代表 GA4 收得到（擋廣告的擴充套件、測量 ID 打錯、`gtag` 沒載入都會讓它靜靜消失）。在正式網址上實際跑一輪遊戲，同時用瀏覽器檢查有沒有真的發出請求——做法見 `references/checks.md` 的「怎麼確認 GA4 真的收到」。

這一層無法完全自動化：即時報表要使用者自己登入 GA4 看。所以最後要明確告訴他「請開 GA4 即時報表確認這幾個事件」，並附上事件名稱清單。

### 4. Google Search Console 待辦清單

**你沒辦法代替使用者操作 GSC**，所以這一段的產出是一份「他要自己去點什麼」的清單，不是宣稱已完成。

先確認這個系列的 GSC 設定（避免給錯建議）：

- 用的是**網域資源**（Domain property），不是網址前綴資源。舊的 non-www 資源只是備查。
- 驗證用的 TXT 記錄在 **Cloudflare**，不在 Vercel。

清單至少要包含：

1. **提交新的 sitemap**（例：`https://www.vibeweb100.com/match-sitemap.xml`）。robots.txt 有列不等於 GSC 知道，兩件事都要做。
2. **對新專案的首頁做網址審查 → 要求建立索引**，至少送預設語言那頁，讓它更快被抓。
3. **幾天後回頭看「網頁」報表**，確認新頁面沒有落在「已檢索 – 目前尚未建立索引」。
4. **不要再提 2026/8 那次演算法降權**——早就解除了，每次驗收都重講一遍只是在放假警報。8 種語言是這個系列的標準值，不是風險，新專案照出即可；要守的是翻譯品質（逐句照該語言的說法寫，不是丟翻譯 API）。真正還沒做的是**把 zh-TW 的頁面做厚**，那是內容工作，跟上線驗收無關，不用每次列進清單。

### 5. 系列文件與內部連結是否同步

新專案上線後有一批文件會過期，而且沒人會主動發現。逐項確認：

- `docs/ARCHITECTURE.md` 第 9 節的進度表有沒有這個專案
- `apps/homepage/README.md` 的「專案一覽」表格（順便看**既有列有沒有過期**——曾經出現過某專案早就上線、表格卻還寫「未部署」）
- 首頁有沒有加上這個專案的卡片，而且**八種語言都有文案**、連結指到對應語言
- `robots.txt` 有沒有列出這支 sitemap
- 該專案自己的 `CONCEPT.md` / `README.md` 狀態是不是還停在「未部署」

## 產出格式

最後給一份彙整，分成三塊：

```
## 已驗證通過
（表格：檢查項目 | 結果）

## 發現的問題
（每項寫清楚：現象、根因、影響、我已經修了還是需要你決定）

## 需要你自己動手的
（GSC 那些我碰不到的，逐條寫成可以照做的步驟）
```

發現的問題如果是程式碼層面而且明確（漏事件、缺標籤、文件過期），**直接修掉再回報**，不要只列清單等使用者發話——這些都是沒有爭議的收尾工作。牽涉到取捨的（例如要不要為了 SEO 補一批內容）才需要問。
