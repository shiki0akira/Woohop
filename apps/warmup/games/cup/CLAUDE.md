# 福杯滿溢（apps/warmup/games/cup）

一支手機傳著玩：輪流往同一個容器加水，一個人加一次就換下一個人，誰讓水溢出來就輸。
玩法與設計決策在 `CONCEPT.md`，這裡只記跟程式碼直接相關的事。

建置與部署跟其他暖場遊戲共用（`apps/warmup`，見那裡的 CLAUDE.md）。2026-11-09 從 `statue` 複製出來，
**已上線（2026-11-10，8 語）**。返回鍵、`<dialog>` 的坑跟定時炸彈一樣，原因寫在 `games/bomb/CLAUDE.md`。

各語言的遊戲名與理由在 `CONCEPT.md` 第四節（八種容器也照各語言的日常說法命名，不直譯）。
首頁插圖是 `woohop-art.js` 的 `art.cup`（水本身當主體、有表情，水面凸出杯口；畫法上的兩個重點寫在那段註解裡）。
首頁清單把手機那一欄標成**不用手機也能玩**（跟竹筍、上樓下樓一樣）：可以準備真的杯子和水來玩。

## `app/app.js` 裡最容易做壞的四件事

**1. 水位一定要從「這一次水開了多久」算出來，不要每個 frame 把增量加上去。**
`levelAfter(start, seconds)` 杯口上下各是一段解析解（見下面「水位模型」）。
累加的寫法在 `requestAnimationFrame` 被節流時（省電模式、背景分頁、開發時的內嵌瀏覽器）
同樣開 1.2 秒會差到好幾倍——第一版就是這樣寫的，測的時候按了 12 次水幾乎沒動。
現在 frame 只負責畫，關水時再用 `heldMs()` 算一次最終水位。
（反過來說：**用背景分頁量「開著不放幾秒溢出」會量不準**，因為偵測溢出在 frame 裡，畫面沒在前景時會延遲。）

**2. 加水只有下限、沒有上限，夾在 `heldMs()` 裡，不要在別的地方補。**
下限 `MIN_POUR_MS` 200ms（不然每個人都可以加 0 秒傳下去，遊戲永遠不會結束）。
**上限刻意拿掉**（老闆 2026-11-09：想加多少是玩家自己的賭注）。

**3. 溢出來的水（`.spill`）要畫在容器輪廓的外側。**
`.spill` 跟水同色，畫在容器裡面會跟水連成一片，畫面上完全看不到。
而且**溢出的時候鏡頭是拉近的**，所以 `spill`／`drops` 還要落在那個杯型的鏡頭畫框裡（見「鏡頭」）。

**4. 鏡頭倍率的上限是「這個杯型最寬的地方要整個留在畫面裡」。**
老闆 2026-11-09 回報「杯肚被切到了」就是倍率超過這條線。杯身可以從畫面**下緣**出去（那像特寫），
左右一旦切到看起來就只是壞掉。改倍率或改杯型的輪廓之後要重新檢查（方法見下面）。

其他幾個小地方：

- **畫面上沒有任何百分比**（CONCEPT.md 2.6）：容器就是儀表板。要加數字之前先讀那一節
- `backToSetup()` **不走 `stopPour()`**：那條路會補最低水量、甚至當場觸發溢出
- `overflow()` 排的 `setTimeout(showEnd)` 可能在使用者已經按返回之後才到，所以 `showEnd()`
  第一行檢查 `screen !== 'play'` 就 return
- **加水是點一下開水、再點一次關水**（不是按住）。一顆按鈕兩個狀態，只接 `click`，鍵盤本來就會觸發 click
- `visibilitychange` 切到背景時當場 `stopPour()`
- 容器的 SVG **一局畫一次**（`renderCup()`，因為每局杯型不同），之後只有 `paintCup()` 改水的 y 與凸起的路徑。
  `cupSvg()` 會呼叫兩次（遊戲畫面一個、結束畫面一個），clipPath 的 id 用 `cupSeq` 分開；
  **結束畫面要畫這一局那個杯型**（`showEnd()` 裡重畫）

## 杯型：一個杯型一筆設定（`SHAPES`）

八種容器，每一局隨機抽一種（老闆 2026-11-09）。**要加第九種只要在 `SHAPES` 再加一筆**
（外加 locale 的 `shapeNotes` 一句、`rulesShapes` 一項），別的地方不用改。

| 代號 | 中文 | 透明 | 手感 | `tenseK` | `weight` | 鏡頭 |
|---|---|---|---|---|---|---|
| `goblet` | 高腳杯 | ✓ | 杯肚寬、杯口收起來，越接近杯口升得越快 | 0.92 | 1 | ×1.33 |
| `glass` | 直筒水杯 | ✓ | 上下一樣寬，線性、最好預測 | 0.85 | 1 | ×1.7 |
| `bottle` | 細頸玻璃瓶 | ✓ | 瓶身寬瓶頸窄，進瓶頸會衝上去 | 1.0 | 1 | ×1.6 |
| `pot` | 陶壺 | ✗ | 看不到水位，壺口又小 | 0.92 | 0.6 | ×1.42 |
| `mug` | 馬克杯 | ✗ | 看不到水位，但杯口寬、早一點看得到 | 0.92 | 0.8 | ×1.5 |
| `measure` | 量杯 | ✓ | 有刻度，可以約好不要超過哪一條線 | 0.85 | 1 | ×1.7 |
| `beaker` | 燒杯 | ✓ | 矮又寬，水位升得最慢，最寬容 | 0.78 | 1 | ×1.25 |
| `flask` | 保溫瓶 | ✗ | 看不到水位**又**瓶口細，最難 | 1.0 | 0.6 | ×2.05 |

- `profile` `[[y, 半寬], …]`（杯底排到杯口）是**水面高度的唯一來源**：`buildLevelToY()` 把它積成
  「裝了幾成水 → 水面在哪個 y」。**瓶頸那種「突然衝很快」是形狀造成的，沒有另外加速度參數**
- `opaque`：水照樣畫在容器裡，再用一層外殼（`shell` 顏色）整片蓋住，只有 `mouth` 那個橢圓裡
  另外畫一層水——所以「看不到水位、但看得到水從壺口冒出來」
- **不透明的那三種不會因為聲音關掉就不抽**（老闆 2026-11-09 改過一次）：杯口看得到水面冒出來，
  沒聲音也玩得下去；開聲音只是更有利（音高可以提早判斷）。聲音關著又抽到不透明時，
  `syncCupNote()` 顯示 `#sound-nudge` 那句提示引導他打開，**不擋路、不強制**
- `weight`：不透明的三種壓低（0.6～0.8），八種合起來不透明約佔三成

## 水位模型（杯口上下是兩條不同的曲線）

`level`：0 空杯 → `RIM_LEVEL`（0.88）剛好到杯口 → 1 溢出。`RIM_LEVEL`～1 是表面張力撐住的那一段。

**杯口以下**：`d(水位)/dt = R0 × (1 + TENSE_K × 水位)`（越滿越快）。
`SIZES` 是「一直開著水從空杯到**杯口**要幾秒」：小杯 2.5／一般 4.5／大杯 6.5。

**杯口以上**（老闆 2026-11-09 實測「第三個就滿出來」之後改的）：

```
這一次加水推進的張力進度 = tenseK × （這一次開水幾秒）^1.6
```

1.6 次方是關鍵：**小口小口加可以撐很久，貪心大口倒就當場輸**。實測（每次點 0.3 秒）
張力段還能再加 6～8 次，點快一點（0.23 秒）10～13 次；一口氣開著不放約 1 秒就溢出來。
要調某一種杯子的凶狠程度改它的 `tenseK`（越大越兇），不要改 `TENSE_POW`。

## 鏡頭：水快滿的時候拉近到杯口

實體玩最好玩的就是杯口那層表面張力，但凸起只有 12～18px，在手機上太小，
所以一進張力（`enterTense()`）就把鏡頭推近，**溢出時維持拉近**，到結束畫面／再來一杯／返回才復原。

- 做法是**外層 div 的 CSS transform**（`.cup-stage` 畫框 overflow:hidden → `.cup-cam` 鏡頭 → `<svg>`）。
  分三層是因為晃動（`.cup.is-tense` 的 rotate）在 `<svg>` 上，鏡頭在外層，兩個 transform 才不會互相蓋掉
- **水位的計算完全沒有跟著動**，鏡頭只是呈現
- 中心與倍率來自杯型的 `zoom`（八種的杯口位置、寬窄都不一樣）。倍率上限＝最寬處要整個進畫面
- 背景小裝飾在 `.cup-decor` 那一層，拉近時淡出（被畫框切一半的圈圈看起來像壞掉）
- `prefers-reduced-motion` 時不做動畫（CSS 把 transition 關掉）

### 改了杯型或倍率之後怎麼驗

在 `/cup/zh-TW/` 的 console 把每個 svg 裡（扣掉 `.cup-decor`、水、clipPath）所有元素的 `getBBox()`
取聯集，跟畫框 `[zoom.x ± 80/scale, zoom.y ± 98/scale]` 比：**左右都要還有餘裕**（上次調完是 3～14 單位），
下緣超出是正常的。八種並排看一次剪影也要做（結束畫面只有 116px 寬，長太像就要調比例）。

## 開場

杯子大小三顆按鈕**固定顯示、不收合**（老闆 2026-11-09：照人數選杯子是重要的一步，收起來會被跳過），
按鈕上寫人數（2–5／6–9／10–12 人，**上限 12 人**），預設「一般」，不存進手機。

開場**不顯示頂欄的聲音開關**（`.cup-app[data-screen="setup"] .game-music { display: none; }`）：
**開始玩才配音樂，這是系列共通的規則**，竹筍、定時炸彈、比手畫腳接力都一樣。

結束畫面的杯子插圖刻意小（`.end-cup` max-width 116px）：**下面的真心話大冒險拉霸要在同一個畫面看得到**。
結束畫面只留「這杯撐過了 N 次加水」一行（「溢在第幾個人手上」是同一個數字，老闆 2026-11-09 劃掉）。

**這個遊戲也可以完全不用手機玩**（主持人準備一個透明杯子和一壺水，真的輪流倒）。
接首頁的時候要跟竹筍、上樓下樓一樣標成不用手機也能玩。

## 音效與配樂

全部 Web Audio 當場合成，不載音檔（跟定時炸彈、竹筍一樣）。

### 音效（三個，直接接 `ctx.destination`，**不受 ducking 影響**）

- **加水**：兩層——噪音過 bandpass（300→1150Hz）墊底，上面一層 triangle＋sine 的音高
  220→660Hz 隨水位爬升。**有音高那一層就是不透明三種容器的儀表板**，改這段之前先想清楚
- **凸起**：一聲 1250Hz 的提示，一杯只響一次
- **溢出**：潑水（白噪音＋低通往下掃）＋兩滴水聲

### 背景配樂（2026-11-09 加，`music` 那一段）

**樂曲本身照搬竹筍**（老闆：「配樂可以和竹筍一樣」）：`NOTE`／`BASS`／`MELODY`、大鼓＋拍手＋
hi-hat＋triangle 貝斯＋square 小旋律、C 大調五聲音階、貝斯一小節一圈、旋律兩小節一句，
跟 `games/bamboo/app/app.js` 的 `music` 同一份。**改之前先去聽竹筍**，要是同一個家族的聲音。

⚠️ **速度整局固定 `MUSIC_BPM` 112，不會越來越快**（老闆 2026-11-09：「不用節奏越來越快！」）。
第一版做過「水位 112→136、張力段 152」，被劃掉了，**不要再加回去**。
緊張感一律靠**音色、和聲、密度**去做。竹筍越玩越快那段（`bpmNow()`）搬過來時就要拿掉。

跟竹筍只有三點不一樣：

1. 竹筍越玩越快看「第幾小節」，這裡**不加速**；跟著水位（`musicTension()` = `level / RIM_LEVEL`）
   變的是密度：hi-hat 過半（`ten > 0.5`）由八分音符補滿十六分音符、八成滿每小節尾巴催一聲高音
2. 多一段**表面張力**（`BASS_TENSE`／`MELODY_TENSE`，`enterTense()` 進去）：一樣的五聲音階、
   **一樣的速度**，但重心從 C 移到 A（關係小調），大鼓變四分音符、hi-hat 全補、旋律升一個八度，
   音量也從 `MUSIC_VOL` 升到 `MUSIC_TENSE_VOL`。跟鏡頭拉近同時發生，是整局的高潮
3. 沒有開場口令，而且每個音都接到 `music.bus`（見下面）

排程跟竹筍一樣是「音訊時鐘＋往前看」（`setInterval` 25ms 排接下來 0.12 秒）。
`musicTick()` 的 `guard` 與「`next` 落後就跳到現在」是給計時器被節流時用的。

### ⚠️ ducking：這一段的第一守則

**配樂不可以蓋掉流水聲的音高**——不透明的陶壺、馬克杯、保溫瓶看不到水位，玩家完全靠音高判斷。
所以配樂的每一個音都掛在 `music.bus` 這一顆 gain 上（相當於竹筍的 `music.master`），
`startPourSound()` 第一行 `duckMusic(true)`、`stopPourSound()` 第一行 `duckMusic(false)`
（**都在所有 return 之前**，水龍頭與 duck 的狀態才永遠一致）。

| | 值 | 說明 |
|---|---|---|
| `MUSIC_VOL` | 0.3 | 平常 |
| `MUSIC_TENSE_VOL` | 0.36 | 表面張力那一段 |
| `MUSIC_DUCK` | 0.055 | 加水時（約 −15 dB） |
| `DUCK_DOWN` | 0.08s | 壓低要快，比水聲自己的 0.07s 淡入還快 |
| `DUCK_UP` | 0.5s | 浮回來要慢，像「水關了音樂自己回來」 |

**改了音量要重測**（方法見下面）：實測水聲的音高在加水時比壓低後的配樂高約 20 dB。

### 什麼時候播

`syncMusic()` 一個地方決定：**在 play 畫面（含抽容器那一段）、還沒溢出、聲音開著**才播。

- **開場（選杯子大小）不播**，全站規則；頂欄音符鍵在開場也是藏起來的
- **抽容器就要有聲音**（老闆 2026-11-09）：`startPlay()` 在 `showScreen('play')` 之後就
  `syncMusic()`，淡入只有 `MUSIC_FADE_IN` 0.25 秒
- **溢出 `endMusic()`**：大鼓一聲＋落到低音 C 收尾，1.5 秒淡掉。**結束畫面不留循環**
- `resetAudio()` 把配樂的節點一起丟掉（它們屬於舊的 context）並記住 `music.ducked = pouring`，
  **要不要接回來一律由 `syncMusic()` 決定**。切回頁面、打開聲音都走這條路
- 切到背景 `stopMusic()`：背景分頁的 `setInterval` 會被節流，排程會亂（跟 `Leader.metronome` 同理）
- `startPour()` 也呼叫一次 `syncMusic()` 保險：切回頁面時新建的 context 可能還 suspended，
  要使用者手勢才 resume，這一下點擊就是那個手勢

**一顆音符鍵管全部**（音效＋配樂，`window.toggleMusic`，存 `localStorage` 的 `woohop-cup-settings`）：
這個遊戲沒有複雜到需要兩個開關，而且水聲本身就是水位計，分開關沒有意義。
所以 locale 的 `soundLabel` 是「聲音」，不是「音效」也不是「配樂」。

**為什麼不直接共用 `window.Leader`**：`Leader.metronome` 是一整個節拍器 UI（要根元素、會畫按鈕
與燈），竹筍的 `music` 是它 IIFE 裡的私有變數。Leader 沒有「只有配樂引擎」可以拿來用，
所以這裡照它們的寫法搬一份。真的要共用得先把配樂引擎從竹筍抽到 `game.js`，那會動到所有遊戲。

### 改了配樂或音量之後怎麼驗（不用耳朵也能驗）

在 `/cup/zh-TW/` 的 console 把 `ctx.destination` 換成一個 `AnalyserNode`（再接回真正的
destination），然後比「配樂的最大峰值」與「加水時水聲音高的峰值」在 200–720Hz 這條帶子裡差多少：

- 配樂單獨（bus 0.3）在這條帶子的峰值約 **−47 dB**
- 加水時 bus 壓到 0.055，水聲音高是穩定的 **−41 dB**，而且峰值頻率跟著水位從 223Hz 一路爬上去
- 兩者差約 **20 dB**＝水聲明顯在前面。**低於 10 dB 就要把 `MUSIC_DUCK` 再壓低**

⚠️ 預覽窗格會每隔幾秒把頁面丟到背景（`document.hidden`），遊戲會照設計停掉配樂，
量的時候要先 `window.addEventListener('visibilitychange', e => e.stopPropagation(), true)` 擋掉。

## GA4

`send_page_view: false`，由 `app.js` 在畫面切換時送 page_view，路徑是 `/cup/{lang}/{setup|rules|play|end}`。

| 事件 | 時機 | 參數 |
|---|---|---|
| `cup_game_started` | 進入加水（含再來一杯） | `game_number`、`cup_size`、`cup_shape` |
| `cup_danger_reached` | 水面第一次凸出杯口（一杯一次） | `pours`、`cup_shape` |
| `cup_overflowed` | 水溢出來 | `pours`、`cup_size`、`cup_shape`、`duration_seconds` |
| `cup_slot_pulled` | 輸的人拉真心話大冒險 | `kind`、`mode` |

`cup_shape` 是給「八種杯型哪一種好玩」用的，上線後看這個決定要不要調權重或刪掉某一種。

**刻意不送每一次加水的事件**：一杯會加十幾二十次，每次送一筆會把資源洗掉，
而「加了幾次」已經在 `cup_overflowed` 裡了（跟定時炸彈同一個結論）。
